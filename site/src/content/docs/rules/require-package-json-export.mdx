This rule requires that if a `package.json` includes `exports` (or `publishConfig.exports`) that an explicit `./package.json` export is included.

## More Details

When a package declares `exports`, that represents the entire API surface for that package.
By including an explicit export for the `package.json`, external tools can more easily consume it (via direct `import`/`require`).
If the package does not export the `package.json`, it makes it harder for tools to load / inspect it.

<Aside type="note">
  If both `exports` and `publishConfig.exports` are declared,
  `publishConfig.exports` is the property that's tested, since it represents the
  set of exports that are shipped externally (when present).
</Aside>

## Examples

<Tabs>
<TabItem label="❌ Incorrect">

```json
{
  "exports": "./index.mjs"
}
```

```json
{
  "exports": {
    ".": "./index.mjs"
  }
}
```

```json
{
  "exports": {
    "import": "./index.mjs",
    "require": "./index.cjs"
  }
}
```

</TabItem>
<TabItem label="✅ Correct">

```json
{
  "exports": {
    ".": "./index.mjs",
    "./package.json": "./package.json"
  }
}
```

```json
{
  "exports": {
    ".": {
      "import": "./index.mjs",
      "require": "./index.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

</TabItem>
</Tabs>

## When Not to Use It

If you're not concerned about providing easier access to your package's `package.json`, then you can safely exclude this rule.
